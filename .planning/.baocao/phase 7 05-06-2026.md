## 1. Chi tiết Kỹ thuật và Cấu trúc Hệ thống

### 1.1. Phần Excerpt / Feed
- **excerpt được lưu ở cột nào:** Cột `excerpt` kiểu dữ liệu `TEXT` trong bảng `posts`.
- **Feed có còn trả full content không:** **Không.** API feed chính (`read_public.php`) và các API danh sách bài viết khác (`read_user_posts.php`, `read_reposts.php`, `read_liked_posts.php`) đã loại bỏ cột `content` bằng hàm `unset($p['content'])` trước khi trả về JSON.
- **Cơ chế hoạt động:**
  - Nếu trường `excerpt` trống hoặc null, backend tự động tách văn bản thuần (strip HTML tags) từ `content` và giới hạn tối đa 150 ký tự làm fallback.
  - Chỉ khi vào trang chi tiết (`PostDetail.jsx` qua API `read_single.php`), nội dung đầy đủ (bao gồm ảnh inline base64 nặng) mới được tải về.

### 1.2. Phần Trash (Thùng rác)
- **Trash dùng deleted_at hay logic nào:** Sử dụng logic Soft Delete với cột `deleted_at IS NOT NULL` trong bảng `posts` và `reposts`.
- **Đảm bảo ID decode:** Các API tương tác thùng rác (`soft_delete.php`, `restore.php`, `permanent_delete.php`, `toggle_visibility.php`) đã được tích hợp bộ giải mã `decodeId()` để xử lý chính xác `post_id` dạng băm nhận được từ React frontend.
- **Mục tiêu cuối:** Người dùng xóa bài viết của chính mình thành công sẽ thấy bài đó nằm trong tab Thùng rác của mình và khôi phục hoặc xóa vĩnh viễn bình thường.

### 1.3. Phần Comments (Bình luận lồng nhau)
- **Comment reply dùng parent_id hay cách khác:** Dùng cột `parent_id` kiểu `INT` trong bảng `comments` liên kết khóa ngoại tự tham chiếu `REFERENCES comments(id) ON DELETE CASCADE`.
- **Logic Validation & Nesting:**
  - Hỗ trợ chính xác 1 cấp phản hồi (flat 1-level nesting). Nếu bình luận cha được chỉ định vốn dĩ đã là một phản hồi (có `parent_id` khác null), bình luận con mới sẽ được tự động trỏ thẳng lên bình luận gốc cao nhất.
  - Validate nghiêm ngặt: `parent_id` phải thuộc cùng một `post_id` với bình luận mới được gửi.
- **Phân quyền xóa bình luận:**
  - Chủ bình luận: Có quyền xóa bình luận của mình.
  - Chủ bài viết: Có quyền xóa **tất cả** bình luận nằm dưới bài viết của mình (bất kể số lượng followers, loại bỏ giới hạn 10k followers trước đây).
  - Admin: Có quyền quản trị tối cao, xóa mọi bình luận.

### 1.4. Phần Notifications (Hệ thống thông báo)
- **Notification lưu bảng nào:** Bảng `notifications` trong cơ sở dữ liệu.
- **Các loại thông báo và điều kiện kích hoạt:**
  - Chỉ kích hoạt khi có hành động chủ động (active):
    - Thích bài viết (`like`) -> Tạo thông báo cho chủ bài viết (Unlike không tạo).
    - Đăng lại bài viết (`repost`) -> Tạo thông báo cho chủ bài viết (Hủy đăng lại không tạo).
    - Bình luận mới (`comment`) -> Tạo thông báo cho chủ bài viết.
    - Phản hồi bình luận (`reply`) -> Tạo thông báo cho chủ bình luận cha.
  - Không tạo thông báo tự sướng (actor_id trùng với user_id của người nhận).
  - **Tránh trùng lặp spam:** Nếu người dùng like/repost lặp đi lặp lại nhiều lần, hệ thống sẽ tự động cập nhật mốc thời gian `created_at = NOW()` và đánh dấu lại thành chưa đọc (`is_read = 0`) trên dòng thông báo cũ thay vì chèn thêm dòng mới vào database.
- **Notification cleanup hoạt động ra sao:** Mỗi lần user tải danh sách thông báo (hoặc gọi API `cleanup.php`), hệ thống sẽ chạy lệnh xóa tự động. Cơ chế cleanup **chỉ xóa thông báo đã đọc (`is_read = 1`) có mốc thời gian đọc `read_at` cũ hơn 3 ngày**. Các thông báo chưa đọc (`is_read = 0`) được bảo vệ an toàn tuyệt đối.

### 1.5. Phần Quản trị Admin
- **Admin user list và post list phân trang server-side thật:** Sử dụng SQL `LIMIT` và `OFFSET` truyền từ frontend qua tham số `page` và `limit`.
- **Admin limit bao nhiêu item/trang:** Mặc định là **15** bài viết / người dùng trên mỗi trang.
- **Search user dùng API nào:** API `/api/users/list.php` được cải tiến nhận tham số `search` truy vấn backend trực tiếp qua câu lệnh `username LIKE ? OR full_name LIKE ?`.
- **Phân quyền truy cập:** Tất cả các API backend admin (`users/list.php`, `admin/read_posts.php`, v.v.) đều kiểm tra JWT token và vai trò `role === 'admin'`. User thường tuyệt đối không thể xem hoặc thực hiện truy vấn.

## 4. Phase 7C - Hotfix Bắt buộc: Trash 0% + Delete Comment 0% (05/06/2026)

Hệ thống tiếp tục được gia cố qua Phase 7C để xử lý triệt để hai lỗi vận hành 0%:

### 4.1. Thùng rác hoạt động ổn định và chính xác
- **Nguyên nhân gốc:**
  - Khởi tạo check `isOwnProfile = currentUser?.uid === id` trong `UserProfile.jsx` dễ bị sai lệch nếu URL chứa ID số nguyên dạng thô `/profile/1` thay vì UID băm, hoặc khi `currentUser` chưa kịp đồng bộ UID từ API login, dẫn đến việc tab Thùng rác bị ẩn hoặc không tải danh sách bài đã xóa.
  - Các API xóa bài viết/repost bị dính PHP Warning nếu request rỗng hoặc không đúng định dạng.
- **Giải pháp xử lý:**
  - **Phục hồi & Đồng bộ:** Nâng cấp `isOwnProfile` kết hợp đối chiếu đồng thời cả `uid` băm, `id` số nguyên từ cả `currentUser` và `profile` được tải về từ server.
  - **Tách luồng tải:** Chuyển `fetchTrash()` và `fetchLikedPosts()` sang một hook riêng biệt chạy ngay khi quyền sở hữu được xác thực `isOwnProfile === true`, giải phóng các cuộc gọi trùng lặp lên server.
  - **Bảo mật và gia cố API:** Gia cố toàn bộ các file API (`soft_delete.php`, `restore.php`, `permanent_delete.php`) để trích xuất tham số an toàn qua mảng kết hợp và kiểm tra `empty()` thay vì đọc trực tiếp thuộc tính từ JSON object, triệt tiêu PHP Warning làm vỡ định dạng JSON trả về.

### 4.2. Xóa bình luận không còn lỗi hệ thống
- **Nguyên nhân gốc:**
  - Request từ React frontend gửi payload JSON nhưng API `be_php/api/comments/delete.php` đọc dữ liệu không an toàn từ `$data->id` khi đối tượng bị null hoặc không có thuộc tính, gây ra PHP Warning/Notice và làm vỡ cấu trúc JSON response.
  - Frontend nhận về HTML cảnh báo thay vì JSON, ném lỗi về mệnh đề `catch` và hiển thị toast chung chung "Lỗi khi xóa bình luận."
- **Giải pháp xử lý:**
  - Nâng cấp `delete.php` hỗ trợ phân tích đầu vào linh hoạt từ cả JSON body và URL-encoded form data (hỗ trợ các key `id`, `comment_id`, `id` qua POST).
  - Sử dụng mảng kết hợp null coalescing `?? []` và kiểm tra `empty()` để tránh mọi cảnh báo PHP.
  - Đảm bảo cơ chế CASCADE trong database tự động dọn sạch thông báo và bình luận con khi bình luận cha bị xóa mà không gây lỗi khóa ngoại.

## 5. Phase 7D - Hotfix Thực tế: CORS Delete Comment + Trash.php Response 0B (05/06/2026)

Hệ thống đã được sửa đổi và kiểm tra lỗi thực tế trên trình duyệt:

### 5.1. Sửa lỗi Xóa bình luận bị chặn bởi CORS Preflight
- **Nguyên nhân gốc:** 
  - Trước đây, trong file `be_php/api/comments/delete.php` và một số API khác, có đoạn code chặn request OPTIONS và `exit()` sớm ở ngay đầu file *trước khi* file `database.php` (và từ đó `cors.php`) được include.
  - Do OPTIONS request thoát ra trước khi CORS headers được thiết lập, trình duyệt coi preflight request thất bại với thông điệp: `No 'Access-Control-Allow-Origin' header is present on the requested resource.` làm chặn đứng phương thức POST thực tế.
- **Giải pháp xử lý:**
  - Loại bỏ hoàn toàn khối kiểm tra OPTIONS exit sớm ở đầu `delete.php`, `trash.php`, `restore.php`, và `permanent_delete.php` để đảm bảo `database.php` được include đầu tiên và CORS headers được trả về trước khi exit.
  - Sử dụng đường dẫn tuyệt đối với hằng số `__DIR__` (ví dụ: `include_once __DIR__ . '/../../config/database.php'`) để tránh các lỗi phân giải đường dẫn tương đối tùy thuộc vào CWD của server PHP CGI/FPM.

### 5.2. Sửa lỗi `trash.php` trả response rỗng (0B)
- **Nguyên nhân gốc:**
  - Preflight OPTIONS của `trash.php` cũng bị lỗi tương tự do đoạn kiểm tra OPTIONS exit sớm trước include, làm trình duyệt chặn đứng request GET tiếp theo và hiển thị kích thước response là 0 B.
- **Giải pháp xử lý:**
  - Tương tự như trên, di chuyển include `database.php` lên dòng đầu tiên để `cors.php` xử lý trước. Gỡ bỏ mọi khối xử lý OPTIONS trùng lặp và thiếu an toàn ở trước phần include.
  - Đảm bảo endpoint `trash.php` luôn trả về JSON hợp lệ thông qua khối `try/catch(Throwable $e)` bắt trọn mọi ngoại lệ hệ thống và định dạng lại shape dữ liệu tương thích hoàn hảo với frontend.

*Báo cáo được lưu trữ tự động trong hệ thống tài liệu dự án.*
